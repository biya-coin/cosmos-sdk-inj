# Injective 接入 SeiDB 分阶段改造方案

## 目标

把 Injective 当前基于传统 Cosmos-SDK / IAVL 的状态存储路径，逐步迁移到 SeiDB 的 `SC + SS` 双层架构，同时尽量不改业务模块语义，把主改动控制在：

- Cosmos-SDK / `store` 层
- `baseapp` 层
- Injective app 启动与接入层
- snapshot / state sync / pruning / migration 相关路径

这不是一次性“换数据库”，而是一次 **存储层架构迁移**。  
因此必须分阶段推进，先缩小风险，再逐步扩大改造范围。

---

## 总体原则

- 先审计，再动代码。
- 先做最小可运行 PoC，再补兼容性。
- 尽量不改 Injective 业务模块，优先改 SDK / store 基座。
- 每个阶段都要有明确退出标准，没过门槛就不要进入下一阶段。
- 迁移、回滚、观测性要从中期就纳入设计，不能最后补。

---

## 阶段 0：基线确认与范围冻结

### 目标

先把当前技术基线确认清楚，避免一开始就带着模糊边界进入改造。

### 要做的事

- 确认 Injective 当前使用的 Cosmos-SDK 版本。
- 确认 Injective 是否维护自己的 SDK fork。
- 确认 CometBFT / Tendermint 版本。
- 找出 app 初始化、`BaseApp` 创建、`CommitMultiStore` 创建入口。
- 找出 snapshot、state sync、pruning、export/import 的入口代码。
- 盘点当前仓库中与 `iavl`、`proof`、`LoadVersion`、历史查询有关的直接依赖。
- 确认是否已有自定义 store wrapper、cache store、root multi store 改造。

### 交付物

- 技术基线文档
- Store 入口映射表
- IAVL 依赖初步清单
- 改造范围边界说明

### 退出标准

- 能回答“现在到底改哪几层，不改哪几层”。
- 能列出 Injective 当前所有核心存储入口。
- 能确认主改动应放在 SDK/store 层，而不是业务模块。

---

## 阶段 1：兼容性审计

### 目标

判断 Injective 当前是否依赖传统 IAVL 语义，哪些可直接兼容，哪些必须适配。

### 要做的事

- 全量扫描代码中对以下能力的依赖：
  - historical proof
  - 历史版本查询
  - iterator 顺序假设
  - snapshot/export/import 语义
  - pruning 参数语义
  - `LoadVersion` / `LoadLatestVersion`
- 识别是否有模块显式或隐式假设底层就是 IAVL。
- 对照 SeiDB 的能力边界，给每个依赖分类：
  - 可直接兼容
  - 需要适配
  - 不兼容，需要重设计
- 梳理 Sei 中真正和该项目相关的代码：
  - `sei-db/`
  - `sei-cosmos/store/`
  - `sei-cosmos/baseapp/`
  - store wiring
  - migration 文档和实现

### 交付物

- 兼容性矩阵
- 风险登记表
- Sei 改造点到 Injective 基座的映射表

### 退出标准

- 每一类 IAVL 依赖都已定位到代码。
- 已明确最小必要移植集合。
- 已识别出会阻塞 PoC 的高风险点。

---

## 阶段 2：最小骨架移植

### 目标

先把 SeiDB 运行所需的最小 SDK/store 骨架引入到 Injective 的技术基座里，但暂时不追求全功能。

### 要做的事

- 从 Sei 的改造中抽取最小必要部分：
  - `store` 层核心结构
  - `baseapp` 接入路径
  - state commitment / state store wiring
  - 必要配置项和启动参数
- 在 Injective 的 SDK 基座里引入新的 store 选择能力，而不是立刻删除旧 IAVL 路径。
- 保留双路径：
  - 旧路径：IAVL
  - 新路径：SeiDB
- 增加 feature flag / app 配置：
  - 是否启用 SeiDB
  - SC/SS backend 配置
  - snapshot / pruning 相关参数
- 确保代码结构上能独立切换，不把原有路径直接打碎。

### 交付物

- 可编译的最小 SeiDB store 骨架
- 新旧存储路径切换开关
- 启动 wiring 初版

### 退出标准

- 项目可以在不开启 SeiDB 时保持原行为。
- 项目在开启 SeiDB 配置后可以完成初始化流程。
- 代码层面已具备进入 PoC 的最小基础。

---

## 阶段 3：本地最小 PoC

### 目标

先验证 Injective 能否在 SeiDB 路径上最小运行，不追求完整兼容。

### 要做的事

- 让本地节点在启用 SeiDB 的情况下完成：
  - app 启动
  - genesis 初始化
  - store mount
  - 首次状态提交
  - 出块
  - app hash 生成
- 先只覆盖最基本链路：
  - 当前状态读写
  - commit
  - restart 后重新加载
- 记录与原 IAVL 路径的行为差异。
- 为 PoC 增加基本日志和 debug 输出，便于定位 commit / load / replay 问题。

### 暂时不追求

- archive node
- 全量历史查询
- 完整迁移工具
- 主网级回滚
- 极限性能优化

### 交付物

- 可本地启动并出块的 PoC 分支
- 基础行为验证记录
- 已知差异清单

### 退出标准

- 启动成功。
- 能出块和 commit。
- 重启后能恢复状态。
- app hash 和基础状态行为可验证。

---

## 阶段 4：功能兼容补齐

### 目标

从“能跑”推进到“核心行为正确”，补齐存储相关关键功能。

### 要做的事

- 补齐并验证：
  - 历史状态查询
  - snapshot
  - state sync
  - pruning
  - export/import
- 修补因语义差异导致的不兼容点。
- 检查 iterator 行为是否影响现有模块。
- 检查 proof 相关行为是否退化或失效。
- 对需要保留旧行为的地方做适配层。
- 对无法保留的行为形成明确限制说明。

### 重点问题

- Injective 是否接受历史 proof 能力变化。
- 现有运维流程是否依赖旧 snapshot 格式。
- 现有节点是否依赖旧 pruning 参数语义。
- 是否存在 RPC / 查询路径间接依赖 IAVL 行为。

### 交付物

- 功能兼容清单
- 不兼容行为列表
- 必要适配补丁
- 测试用例补充

### 退出标准

- 关键查询和出块行为正确。
- snapshot / state sync / pruning 至少在测试环境可用。
- 已经清楚哪些行为可以支持，哪些必须放弃或改运维流程。

---

## 阶段 5：迁移方案设计

### 目标

在功能兼容基本成立后，设计从旧 IAVL 节点迁到 SeiDB 的路径。

### 要做的事

- 定义迁移对象分类：
  - validator
  - full node
  - archive node
- 设计迁移路径：
  - 新节点直接启用 SeiDB
  - 老节点迁移到 SeiDB
  - 归档节点单独策略
- 明确迁移前提：
  - 停机窗口
  - snapshot 来源
  - 数据一致性校验
  - 回滚条件
- 如果需要，设计离线迁移工具或迁移脚本。
- 定义状态一致性验证方法：
  - app hash 比较
  - 高度对齐
  - 关键模块状态抽样比对

### 交付物

- 迁移设计文档
- 节点类型迁移手册
- 数据一致性校验方案
- 回滚触发条件说明

### 退出标准

- 每类节点都有明确迁移路径。
- 迁移失败时有清晰回退方案。
- 可以在测试网或准生产环境演练。

---

## 阶段 6：性能验证与观测性建设

### 目标

确认这次改造确实带来存储收益，而不是只增加复杂度。

### 要做的事

- 建立对比测试：
  - IAVL 基线
  - SeiDB 路径
- 重点观察：
  - commit 延迟
  - 启动耗时
  - restart 恢复耗时
  - state sync 耗时
  - 磁盘占用增长
  - 内存占用
  - pruning 效果
- 增加监控指标：
  - SC commit 延迟
  - SS 写入延迟
  - snapshot 生成耗时
  - replay 耗时
  - migration 进度
  - store 错误率
- 做压力测试和故障恢复演练。

### 交付物

- 性能对比报告
- 监控指标说明
- 故障注入与恢复记录

### 退出标准

- 至少在关键指标上有可测收益。
- 没有出现不可接受的资源回退。
- 运维侧能观察和定位 SeiDB 路径的问题。

---

## 阶段 7：测试网灰度

### 目标

在接近真实环境的条件下验证稳定性和迁移流程。

### 要做的事

- 先在内部测试网或开发网启用 SeiDB。
- 再选择小规模灰度节点运行。
- 演练：
  - 全新启动
  - 重启恢复
  - state sync
  - pruning
  - 节点升级
  - 节点故障恢复
- 持续记录稳定性问题和性能表现。
- 修复灰度中暴露出的边界 bug。

### 交付物

- 灰度运行报告
- 问题清单与修复记录
- 上线前最终风险清单

### 退出标准

- 测试网运行稳定。
- 核心运维动作都已演练通过。
- 剩余风险处于可接受范围。

---

## 阶段 8：主网迁移与生产化

### 目标

在受控条件下把 SeiDB 引入生产环境。

### 要做的事

- 明确主网切换窗口和执行步骤。
- 提前发布升级说明、节点操作手册和回滚手册。
- 迁移时按节点角色分批推进。
- 监控主网切换后的：
  - commit
  - 出块稳定性
  - state sync
  - 磁盘增长
  - 异常日志
- 预留快速回滚和临时降级方案。

### 交付物

- 主网执行 Runbook
- 节点升级说明
- 回滚手册
- 上线后观测报告

### 退出标准

- 主网稳定运行。
- 节点升级路径清晰可复用。
- 运维团队能独立处理常见故障。

---

## 各阶段之间的依赖关系

### 必须严格先后推进的部分

1. 阶段 0 先于所有阶段。
2. 阶段 1 先于阶段 2 和阶段 3。
3. 阶段 3 通过后，才能进入阶段 4。
4. 阶段 4 基本稳定后，才能设计可信的迁移方案。
5. 阶段 5 和阶段 6 可以部分并行，但都要先建立在阶段 4 的基础上。
6. 阶段 7 必须在迁移方案和观测性准备好之后再开始。
7. 阶段 8 只能在测试网灰度通过后执行。

---

## 推荐实施顺序

1. 先做阶段 0 和阶段 1，拿到完整依赖图和兼容性矩阵。
2. 再做阶段 2，建立最小骨架和双路径切换能力。
3. 然后做阶段 3，验证本地最小 PoC。
4. PoC 跑通后，进入阶段 4，补齐关键功能兼容。
5. 兼容性基本成立后，同时推进阶段 5 和阶段 6。
6. 最后进入阶段 7 和阶段 8。

---

## 一句话结论

这个项目最稳妥的推进方式，不是一次性把 SeiDB 整包替进 Injective，而是：

**先确认 Injective 对 IAVL 的依赖，再移植最小 store/baseapp 骨架，先跑通本地 PoC，再逐步补历史查询、snapshot、state sync、pruning、迁移和观测性，最后才进入测试网和主网。**
